01 — Overview

A controlled state space, not a broken hash

A generic collision against the complete 256-bit output of SHA3-256 is outside the reach of any machine. Truncating that output to its first n bits produces a controlled state space in which generic collision-search algorithms can actually be implemented, measured and compared — without making any claim that the hash function has been broken. HashFrontier is the apparatus built around that setting: one frozen configuration, three search engines, eight widths, and an evidence file for every reported pair.

Exact leading-bit truncation

One shared routine masks the digest to exactly n leading bits for every engine. Non byte-aligned widths keep ⌈n/8⌉ bytes with the final byte masked and all padding bits cleared — 70 bits occupies nine bytes of which only the top six are meaningful, and a state with non-zero padding is rejected outright.

Unambiguous message encoding

GHCF v1 length-delimits the domain, run identifier, salt and algorithm name, then appends a two-byte width and an input-kind tag. Delimitation prevents ambiguous decompositions such as the domain/run pair ab/c versus a/bc, and the tag stops one byte string being read as both a counter and a walk state.

Three engines, one hash core

A storage-intensive birthday table, a memory-efficient distinguished-point walk and an independent Pollard-rho/Floyd search all call the same truncation and encoding code. What differs between them is only what they choose to remember — which is exactly the variable the study is trying to measure.

Recoverable multi-process execution

Immutable manifests, atomic JSON checkpoints and coordinator-owned SQLite state make a run safe to interrupt and resume at any point. A resumed run rebuilds the expected manifest and rejects a mismatch rather than silently continuing an incompatible experiment.

Portable, independently verified evidence

Every accepted result stores both inputs, both canonical messages, both complete SHA3-256 digests and the matching truncated digest. A separate verifier rebuilds and recomputes all of it from the JSON alone — no live database — and a tampering test confirms it rejects a modified file.

Bounded runs stay bounded

Seven of the 24 rows did not produce a committed collision. They are reported as measured work at a frozen stop point — an evaluation budget reached, or a controlled interruption — and are never re-labelled as evidence that a collision at that width is impossible.

Mandatory claim boundary. A verified collision here means two distinct GHCF v1 messages have equal first n bits under SHA3-256. The complete 256-bit digests in every supplied collision file are different. A bounded or interrupted run means only that the recorded work did not produce a committed collision before that run stopped — it does not represent that a collision exists, nor that one cannot. No complete SHA3-256 collision is claimed.
02 — Architecture

Workers hash; the coordinator decides

GHCollision is a reusable Python package rather than three unrelated scripts. Every command-line entry point first constructs the same immutable configuration, dispatches one of the three engines, and writes evidence into a run-specific workspace. One rule keeps the result trustworthy under multiprocessing: worker processes perform hashing only.

1

Freeze the configuration

bin/ghcollision

The CLI builds a frozen HashConfig binding algorithm, truncated width, domain, run identifier and salt. Its constructor normalises the algorithm spelling, rejects variable-output functions such as SHAKE, validates 2 ≤ n ≤ 256, and derives the GHCF v1 message prefixes and the exact truncation mask once, up front.

manifest.json domain = MSSD-Security-Labs-Generic-Hash-Collision encoding version 1
2

Allocate deterministic work

engine coordinator

The coordinator assigns non-overlapping, self-contained work units: a chunk identifier plus start counter and count for birthday; one chain identifier for DP; one attempt identifier for rho. Queues are bounded by a per-engine queue_depth, and a single keyboard interrupt requests a controlled stop that keeps committed batches, chains and attempts durable.

8 worker processes bounded queues deterministic work identifiers
3

Hash in worker processes

ghcollision/workers.py

Worker initialisation reconstructs and caches the immutable configuration, the counter and state prefixes, the state width, the final mask and the engine-specific limits. Birthday workers return a packed byte buffer of reduced digest plus 16-byte counter; DP workers return an endpoint with its start and length, or a capped-chain record; rho workers return a recovered collision, a cap status or a restart status. Workers never write to the database.

packed record batches endpoint + length attempt status + counted hashes
4

Recover and accept a candidate

birthday · distinguished · rho

A potential pair is never accepted from a database key alone. The coordinator calls the shared result constructor, which re-encodes both inputs and recomputes both complete digests. DP aligns the two trails, walks them in lockstep and recovers the distinct merge predecessors; a path that coincides without yielding distinct predecessors is recorded as a false merge rather than a result. Progress is committed transactionally with write-ahead logging.

checkpoint.json SQLite + WAL workspace collision.json / summary.json
5

Verify and summarise independently

ghcollision verify

The standalone verifier repeats the acceptance logic from the serialised file rather than trusting the engine's in-memory objects. The matrix summariser then consolidates every workspace into one frozen snapshot in JSON, CSV and Markdown — the single source from which every number on this page is drawn.

matrix_summary.json matrix_summary.csv verification_all_collisions.txt

Resume safety

A new workspace receives an immutable manifest.json containing the hash configuration, engine, software version, environment and engine parameters. Resumption reconstructs the expected manifest and rejects a mismatch — which is why changing worker count, DP bits, queue depth, chain cap, run identifier, salt or width requires a new workspace rather than silently continuing an incompatible run.

  • manifest.json — immutable identity and execution parameters
  • checkpoint.json — latest durable counters, resource indicators, status
  • SQLite database(s) — search index and completed-work log
  • collision.json — portable verified evidence when a collision is found
  • summary.json — portable bounded / interrupted evidence when it is not

03 — The width sweep

Eight widths, each roughly a thousand times the last

The experiment is a full factorial matrix over three engines and eight truncated widths — {birthday, DP, rho} × {10, 20, …, 80}. Because the generic work factor is O(2^(n/2)), every ten bits multiplies the expected effort by about 32, and the storage a birthday table would need by about the same. The 10-to-80-bit matrix therefore spans many orders of magnitude, and the width-specific parameters are declared rather than hidden.

Why storage decides it first

Raw packed records at the generic birthday scale E[Q] ≈ √(π/2)·2^(n/2), multiplied by the reduced-digest-plus-counter record size. SQLite pages, indices, WAL files and filesystem allocation add overhead on top.

Log-scaled. At 80 bits the raw records alone exceed 32 TiB before any database overhead — a planning estimate, not a measured allocation, and the reason the birthday evaluation caps at 60, 70 and 80 bits were deliberately reduced rather than raised.

Width-specific parameters

BitsBirthday capDP bits dMean chainRho attempt cap

The DP schedule sets d = ⌊0.3n⌋, giving a mean chain length of 2^d and a cap of 8 · 2^d. Rho applies a 100-million-hash cap per attempt from 50 bits onward — that cap bounds one attempt, after which the engine schedules another rather than terminating the search.

Independent variables

Engine and truncated width. Nothing else moves between rows.

Shared controls

SHA3-256, GHCF v1 encoding, the domain string, an empty salt, toolkit version 1.2.0 and the same recorded Linux/Python environment.

Frozen snapshot

Every table and plot is generated from one matrix_summary.json; every successful row is cross-checked against its own collision.json.

04 — Method

The controls that make the comparison mean something

A matching database key is not evidence. Before any pair is called a collision it has to survive a chain of definitions: what exactly was hashed, which bits are being compared, what counts as completed work, and what a run that stopped early is allowed to claim.

GHCF v1 canonical message layout

GHCF\x01magic · 5 B
L(D) ‖ Ddomain
L(R) ‖ Rrun id
L(S) ‖ Ssalt
L(A) ‖ Aalgorithm
n₁₆width · 2 B
00 | 01input kind
c₁₂₈ | x⌈n/8⌉counter or state

Every L(·) is a two-byte big-endian length field. Counters always occupy 16 bytes; states occupy exactly ⌈n/8⌉ bytes and must carry zero padding bits outside the configured width. Chain and attempt starts are derived deterministically with SHAKE-256 over a separate start-domain string, the immutable run prefix and a 128-bit sequence identifier — used purely as an internal expander, never as the collision target — so repeating a run with the same immutable configuration recreates the same starting states.

Acceptance criteria

A collision is accepted only if all five hold. The standalone verifier re-checks every one of them from the serialised file.

  • The two canonical messages are distinct.
  • Both messages reconstruct from the configuration and stored inputs.
  • Both complete SHA3-256 digests recompute exactly.
  • Both stored reduced outputs recompute exactly.
  • The two reduced outputs are equal for exactly n leading bits.

Evidence controls

Four rules govern how the frozen matrix may be read.

  • All summary plots use one frozen matrix_summary.csv; later checkpoint changes are not mixed into the snapshot.
  • Successful rows must have a verified collision.json, and bounded rows are never re-labelled as failures of the hash function.
  • The same encoded-message and truncation code is used by all three engines.
  • Rho-80, which completed zero counted hashes, is shown for completeness but excluded from every substantive rate comparison.

Outcome definitions

Verified
A collision.json exists and passes the standalone verifier.
Evaluation budget
A birthday run reached its configured global evaluation cap.
Interrupted
A run was stopped; summary.json or checkpoint.json preserves the work completed at that point.
Not a row
Missing or invalid evidence is never converted into a successful row.

Recorded per row

  • Counted hash evaluations
  • Elapsed seconds and aggregate counted rate
  • Status and verified-collision flag
  • Birthday-model probability at the counted work level
  • Configured worker count and engine-specific parameters
  • Coordinator and peak reported worker RSS, and an estimated process-RSS upper bound
  • Workspace storage at the result or checkpoint

Inside the code

05 — Search engines

Three ways to find the same thing

All three engines share one truncation routine, one message encoding and one coordinator. They differ entirely in what they choose to remember — and that single difference is what produces the time–memory behaviour the matrix measures.

Birthday table

store everything

Enumerates counters c = 0, 1, 2, …, encodes each as a canonical message, computes Hn(mc) and inserts the pair into a sharded SQLite table. A collision is an immediate table match. The submitted matrix uses 16 shards, 50,000 candidates per batch and queue depth two; completed batches commit in chunk-identifier order so the next counter is always a contiguous, durable frontier.

T = O(2^(n/2))   M = O(2^(n/2))

Advantage: conceptual simplicity and direct collision detection. Cost: nearly one record per candidate.

Distinguished points

store the endpoints

Iterates F(x) = Hn(EncodeState(x)) from a deterministic start until the state's first d bits are zero. Only the chain identifier, start, endpoint and length are stored. When two chains reach the same endpoint they merged earlier: the coordinator aligns their remaining lengths, retraces both trails and identifies the distinct predecessors u ≠ v with F(u) = F(v).

chain ≈ 2^d   d = ⌊0.3n⌋   cap = 8·2^d

Advantage: far fewer records than a full table. Cost: reconstruction work and occasional capped trails.

Pollard rho / Floyd

store almost nothing

Advances a tortoise once and a hare twice per step until they meet, then resets the tortoise to the start and walks both in lockstep to recover two distinct predecessors mapping to the same state. Each attempt starts deterministically from its attempt identifier and reports one of three statuses — collision, capped, or restart.

t ← F(t)      h ← F(F(h))

Advantage: very little persistent state. Cost: independent attempts share no partial work.

Expected qualitative properties, stated before the runs. Section 06 tests each of them against the measured matrix. One constraint holds throughout: the three algorithms do not generate statistically identical sample sequences, so the birthday approximation is used as an indicative normalisation of counted work, not as a proof that every walk method has the same success distribution as independent sampling.

06 — Results

No engine dominates the whole range

Birthday search verified collisions through 40 bits, Pollard rho through 60, and distinguished points through 70. These are the observed frontiers of the submitted run matrix under one execution plan — not mathematical limits of the algorithms. A different random mapping, a longer run, a different DP parameter or a different worker allocation may move which width succeeds.

Birthday — verified to 40 bits

The 40-bit run processed 1.2 M hashes in 11.10 s at 108,151 hashes/s, storing 1,190,775 records across 16 shards in 125.15 MiB. At 50 bits the workspace reached 495.60 MiB and the RSS upper bound 781.79 MiB — the two highest values anywhere in the matrix — before interruption, and without reaching its 50 M cap.

DP — verified to 70 bits

The 70-bit run used 21 distinguished bits, completed 2,624 chains and stored 2,623 endpoints. One duplicate endpoint joined chains 2101 and 2616; retracing cost 7,152,782 extra hashes, found no false merge, and recovered the distinct predecessors. Total 5,310,915,809 hashes in 56 m 53 s at 1.556 M/s — in 4.16 MiB.

Rho — verified to 60 bits

At 60 bits rho completed 893 attempts and 89,236,658,241 hashes over 13 h 27 m. The winning attempt was number 897 and used only 36,659,133 of those hashes itself — the remainder is restart work that independent attempts cannot share. Workspace stayed at 3.68 MiB.

At 50 bits — all three comparable

Birthday-50 was interrupted before its cap, so its bars are partial work — and the storage bar is exactly the point.

At 60 bits — DP versus rho

Both rows are verified collisions at the same width, reached at very different prices.

Birthday pays in storage

Its partial 50-bit workspace is 122× larger than the successful 50-bit DP workspace, and its RSS upper bound 3.93× higher. It becomes impractical well before the generic work scale at 60–80 bits.

DP pays in reconstruction

It reconstructs only when two endpoints match. Its successful 70-bit run consumed 5.31 billion counted hashes while holding just 4.16 MiB — the best observed balance between search depth and persistent storage on this VM.

Rho pays in repeated work

Only 54.07 KiB at 50 bits, but independent attempts share no progress. At 60 bits it needs 327.8× the counted hashes and 181.5× the elapsed time of DP — a consequence of this independent-restart implementation, not proof of a 327-fold algorithmic gap.

08 — Discussion

A frontier is an observation, not a limit

The four research questions are answered from the frozen snapshot, and each answer is qualified by what the snapshot can and cannot support. Being explicit about the second part is what makes the first part worth stating.

RQ1At which widths does each engine produce an independently verified collision?▼

Birthday verified through 40 bits, DP through 70 and rho through 60 — DP is therefore the widest successful method in the present evidence set. The seven non-successful rows consist of three birthday evaluation-budget stops (60, 70, 80), the birthday-50 interruption, the DP-80 interruption, the rho-70 interruption and a rho-80 launch with zero completed hashes.

These frontiers are not mathematical limits. A different random mapping, a longer run, a different DP parameter, a different worker/core allocation or a different implementation may alter which width succeeds.

RQ2How do counted work, runtime, throughput, memory and storage change with width and engine?▼

The matrix strongly supports the expected storage ordering. Birthday stores nearly one record per retained candidate, reaching 495.60 MiB after 16.05 million 50-bit evaluations. DP stores completed endpoints and reconstructs only on a match — its successful 70-bit run uses 4.16 MiB despite 5.31 billion counted hashes. Rho stores little path state (54.07 KiB at 50 bits) but shares no progress between attempts: it requires 5.15× the counted hashes and 12.91× the elapsed time of DP at 50 bits, and 327.8× the hashes and 181.5× the time at 60 bits.

Birthday's end-to-end throughput is lower because hashing is coupled to record packing, shard partitioning, primary-key lookup and durable insertion. DP and rho spend a much larger fraction of high-width runtime inside repeated transition hashing. The rate curves therefore reflect implementation work, not merely the cost of SHA3-256.

RQ3Is there a complete reproducibility path from input construction to standalone verification?▼
  • GHCF v1 defines exactly what is hashed.
  • Immutable manifests bind configuration, environment and engine parameters.
  • Deterministic work identifiers and starting states make replay possible.
  • Checkpoints and coordinator-owned SQLite state preserve completed work.
  • A resumed run rejects parameter mismatches rather than silently corrupting the experiment.
  • Collision files contain complete messages and full digests, not only reduced outputs.
  • A separate verifier independently rebuilds and recomputes every claim.

26 passing tests and the 17-of-17 standalone replay provide concrete evidence for this chain. Reproducibility of the collision evidence is however stronger than reproducibility of the performance numbers, which depend on CPU allocation, hypervisor scheduling, storage device, background load and process oversubscription.

RQ4What practical limiting point does the evidence support at 80 bits?▼

DP-80 is the most informative high-width observation: 288.289 billion hashes at 2.345 million hashes/s over 34.14 hours, corresponding to an idealised birthday-model probability of 3.38%. The work for 50% probability is approximately q₀.₅ ≈ √(2 ln 2)·2⁴⁰ ≈ 1.295 × 10¹² — about 6.39 days from zero at the observed end-to-end rate, or roughly 4.97 further days beyond the frozen checkpoint.

The snapshot therefore supports the conclusion that 80 bits is a multi-day rather than sub-day target on this recorded configuration, and nothing stronger. Rho-80 cannot be used to estimate a frontier because it completed zero counted hashes; birthday-80 is not comparable to a full search because its one-million-evaluation cap corresponds to a collision probability of 4.14 × 10⁻¹³. The only substantive 80-bit evidence is the interrupted DP run.

Threats to validity

Single-run stochastic variation

Only one frozen row is analysed per engine–width pair, and collision time has high variance. Early successes such as DP-60 at 272.25 million evaluations must not be treated as expected values; repeated independent run identifiers are required to estimate median work and confidence intervals.

Unequal stopping rules

Birthday uses global evaluation caps, whereas DP and rho were generally stopped by collision or manual interruption, and rho also applies per-attempt caps. The matrix compares realistic method-specific operation, not equal work budgets.

Walk dependence

The birthday approximation assumes independent uniform samples. DP and rho generate iterated walks with merging and cycles, so the stored birthday_model_probability values are useful scale indicators, not calibrated p-values for the exact walk processes.

Hardware and oversubscription

The manifests report four logical CPUs and eight workers. No genuine 8- or 16-core measurement is present, so worker oversubscription may alter context-switching, cache behaviour and throughput. CPU model, RAM size, disk type, VM host contention and affinity are not recoverable from these results.

Memory measurement

The process-RSS field is an estimated upper bound based on coordinator and reported worker values, not a continuously sampled aggregate peak. Workers may report memory at task completion rather than at the true peak. Storage values are more directly auditable, though they depend on WAL and checkpoint timing.

Security interpretation

The experiment neither exploits a structural weakness in SHA3-256 nor demonstrates a collision in the complete digest. The framework is appropriate for controlled education and benchmarking; presenting these reduced-output pairs as evidence that SHA3-256 is broken would be technically incorrect.

Repository, tests and reproduction

GHCollision v1.2.0 — a reusable Python package with three coordinated engines, a standalone verifier, a benchmark-derived limit planner and a matrix summariser, all sharing one hash and encoding core.

What the test suite guarantees

  • Exact leading-bit truncation at byte-aligned and non-aligned widths, including final-byte masking and padding-bit rejection.
  • GHCF v1 encoding round-trips, and that counters and states can never be decoded interchangeably.
  • Deterministic starts reproduce for a given immutable configuration and sequence identifier.
  • Engine behaviour for all three search strategies, including capped and restart paths.
  • Result construction rejects equal messages and non-matching reduced outputs.
  • Standalone verification of portable files, plus legacy prefix ‖ input pair compatibility.
  • Recovery from a narrow crash window in which a duplicate endpoint is committed but the portable collision file has not yet been written.

26 tests in total, all passing on the submitted version, and all runnable without any real experiment data.

The pipeline passes no overall --time-limit. Birthday remains bounded by global evaluation caps and rho by per-attempt caps, but a DP run continues until collision or manual interruption — which is why several rows are labelled interrupted. Removing both --time-limit and --max-evaluations from a direct birthday run makes it globally unbounded, and unsafe at high widths: persistent storage can grow until the VM disk is exhausted.

Recommended future work

  • Repeat each 40–80-bit configuration with several independent run identifiers and report medians and distributions.
  • Re-run worker sweeps on VMs with genuinely allocated 1, 2, 4, 8 and 16 logical CPUs for real speedup evaluation.
  • Add matched wall-time and matched hash-budget comparisons alongside the collision-until-found runs.
  • Tune distinguished bits against measured chain throughput and endpoint-storage constraints.
  • Measure process memory externally at regular intervals and record CPU model, RAM, disk and hypervisor allocation.
  • Investigate cooperative parallel rho variants that share distinguished endpoints rather than relying only on independent Floyd attempts — the highest-value extension.
  • Retain check-summed, immutable evidence snapshots for each newly generated result set.
